# rtl/igs023.sv — commentary

Extended commentary for the CPU-VRAM arbitration model.  Evidence base:
`util/vram_bench/results/LA_FINDINGS.md` (logic-analyzer captures of a real
IGS023 board, benchmark data in the same directory).

### `vram_as_sel`

> wire vram_as_sel = ~cpu_as_n && (cpu_addr[23:20] == 4'h9);

The 68000 asserts UDS/LDS one CPU clock later on writes than reads, and the
external chip select (`address_translator`) is gated on the data strobes, so
a CS-edge-started VRAM cycle makes every write one CPU clock slower than a
read.  Measured on real hardware (`util/vram_bench`), a VRAM write costs
exactly the same as a read, so the real 023 starts its cycle from AS +
address.  The FPGA does the same: the CPU VRAM cycle begins on the AS edge,
and the per-phase strobe gates on `vram_we_n` keep write byte-enables
correct (the strobes are valid well before each HOLD commit).

### The decoded VRAM mux schedule (`headstart_cnt`, `slot_phase`, `fetch_line`)

On every fetched line the real 023 time-slices the VRAM address bus:

1. **FG line-buffer fetch** (~13.4 µs on hw): CPU locked.  Modeled by the
   existing `fg_real_vram_master` window (464 ce_33m ticks, 13.7 µs).
2. **BG head-start** (BG prefetch, CPU still locked): length shrinks by one
   pixel slot per pixel of BG scroll alignment within the 32 px tile.
   bg_x sweep: hole end = 11.8 µs − 100 ns × (scroll mod 32) after sync,
   single-bin deterministic.  hw total hole is 17.8 µs at alignment 0.
   The head-start counter lives in IGS023_BG (`headstart` output, loaded at
   the fg_real_vram_master falling edge); see
   docs/comments/rtl/igs023_bg.sv.md for its calibration.
3. **Steady state** (live immediately from the hole end): 800 ns microcycle
   = BG half-cycle (4 slots, its {0,1,2,1} byte scan) then a contiguous
   4-slot CPU window [+400,+700].  The union of post-hole commit phases
   across la_movem/la_bgx00/la_longw fits exactly this and nothing narrower;
   word's apparent 4×700 ns "transient" is its ~650 ns request spacing
   sliding through the window before locking at 800 ns.  The access held
   during the hole commits AT the hole end, ahead of BG's first half-cycle.
4. **Vblank lines** (and `bus_master`): unscheduled, CPU free.

The slot counter is anchored at the hole end: held at 0 through the
head-start so the microcycle (BG half first, CPU window at +400..+700)
starts exactly at the hole end.

### `cpu_slot_grant` / `cpu_boundary_grant` — the soft window edge

> wire cpu_slot_grant = slot_phase[2];
> wire cpu_boundary_grant = (slot_phase == 3'd0) & (subslot < 3'd2);

The CPU window is the second half of the microcycle (slots 4-7), but its
trailing edge is SOFT: a NEW request pending at the microcycle boundary wins
slot 0 and completes there.  Evidence (la_wall2, free-running word_w):
post-chunk-gap words commit at phase 0-20 with both WR pulses inside slot 0
— ~90% of chunk re-entries; the other ~10% wait for the window (the 3100 ns
gap-length population).  A mid-access CONTINUATION does not win slot 0: a
late slot-7 write's odd byte loses it to BG and waits for the donated
slot 3.  Per-slot arbitration, with new-request beating BG only at slot 0.
On hardware every 100 ns slot carries a bus event — BG fills whatever the
CPU does not take, so the window is a preemption right, not exclusive
occupancy.

### `access_straggle` — window-edge write stretch

A write dispatched at the window edge STRETCHES on real hardware: its odd
byte slips to the LAST slot of the following BG half (slot 3 — BG's
redundant byte-1 re-read, which it donates).  la_wall2 evidence: word
writes with byte pulses 336 ns apart, byte0 at the window end, byte1 at
anchor+1100; ~250/frame in free-running ALL mode — this is the entire hw
write-vs-read ALL-window deficit (word_r 14505.6 vs word_w 14307.2 apf).
Reads complete in-slot at SRAM speed (~30 ns/byte, cf. the 33.87 MHz FG
crawl) and never straggle.  The access held through the hole is exempt:
its two pulses commit back-to-back at the hole exit.

On hardware the outcome at the window edge looks statistical (per-frame LA
counts vary ±15 words with a stable long-run mean) because the 68k runs on
its own 20 MHz crystal: the CPU-to-slot-grid phase slips ~85 ns per frame,
sweeping every knife edge through all alignments.  That drift is modeled in
the ce_20m generator (PGM.sv `CPU_CEN_STEP`), so the fit rule here stays
deterministic.

### `cpu_slot` — BG yields to the CPU

During CPU grant slots the BG fetcher yields the bus (the real 023's BG
never occupies CPU slots); outside the hole BG has prefetch slack, so the
deferral is absorbed by its line buffer.  The slot-3 term lets a straggling
write's odd byte use BG's donated redundant read slot.

### `held_in_hole`

A request pending while the hole is locked commits at the hole exit, ahead
of BG's first half-cycle; followers wait for the regular CPU window (hw:
movem/long second word commits at hole_end+400, the first window slot).
The flag persists to access completion so the hole-exit access commits both
bytes back-to-back, and clears on completion so a follower cannot inherit
the exemption.

### `RAM_ACCESS_VRAM_LOW`/`HIGH` order and byte-pair cycling

Even (low) byte first, then odd — matches the WR# pulse order captured on
real hardware.  Both halves always cycle even for byte accesses (measured:
a byte read costs the same as a word read); writes are gated per-phase by
the matching data strobe so a byte write only commits its addressed half.
The SETUP+HOLD pair per phase gives writes a second commit edge — the 68000
asserts UDS/LDS ~50-60 ns after AS on write cycles, later than a 1-tick
phase would sample (a 1-tick restructure silently dropped write bytes;
see branch history commit e022695 and its revert).

### `bg_headstart`

The BG head-start lock (hole phase 2) is owned by IGS023_BG and imported
here as a level: it extends `vram_hole` and holds `slot_phase` at 0 so the
microcycle grid anchors at the hole end.
